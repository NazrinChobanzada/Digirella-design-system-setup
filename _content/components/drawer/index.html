A drawer slides in from the edge of the viewport to surface related content or actions without navigating away from the current page.

Overview

Drawers keep the user in context. Unlike a dialog, a drawer occupies a portion of the screen while the underlying page remains partially visible behind the scrim. This makes them well suited for tasks that need a lot of space — editing a record, reviewing order history, configuring a filter panel — without the feeling of a hard interruption that a dialog creates.

Guidelines

When to use

Choose a drawer when the task requires enough content or interaction that a dialog would feel cramped, but you still want the user to see — and return to — the page behind it. Use a dialog for short confirmations and brief forms where the binary decision is more important than the surrounding context.

Content guidelines

Every drawer has three regions: a header, a scrollable body, and a footer. Each region has a clear job and should not be re-purposed.

Header

The title names the task or object being worked on. Keep it to one short phrase: "Edit profile", "Order #4821", "Filter results". Always include a visible close button — typically a ✕ icon with an aria-label — in the header's far corner. Do not rely on the scrim alone to close the drawer.

Body

The body scrolls independently. Treat it like a contained page: use standard form spacing, group related fields under headings, and do not rely on the footer staying in view to explain what the form does. Someone who has scrolled down to field 15 should still be able to understand what they are doing without scrolling back up.

Footer actions

One primary action, right-aligned. A cancel or dismiss to its left. Nothing else. The primary action completes the task: "Save", "Apply", "Confirm order". Never put a third action in the footer — if the task branches, that branching belongs in the body, not the footer.

Behaviour

Opening & closing

A drawer opens in response to a deliberate action — a button press, a row click, a navigation item selection. It never opens automatically. The panel animates in from the edge over --transition-enter (220ms, ease-out). The scrim fades in simultaneously.

Ways to close

Overlay clickClicking or tapping the scrim dismisses the drawer and returns focus to the trigger. This is the most common gesture, so it must always work.
Escape keyPressing Escape closes the drawer. If there are unsaved changes, show an inline confirmation within the drawer body before closing — do not show a second dialog on top.
Close buttonThe ✕ in the header always closes the drawer. It is the mandatory, always-visible escape. Do not hide it on smaller screens.
Explicit submit or cancelThe footer buttons either submit and close (primary) or discard and close (ghost cancel).

What does not close the drawer

Scrolling the body does not close the drawer. Clicking inside the panel does not close the drawer. These interactions are intentional and must not be interpreted as dismissal.

Unsaved changes

If the drawer contains a form with unsaved changes, intercept the close gesture and show a message within the drawer: "You have unsaved changes. Discard them?" with "Keep editing" and "Discard" actions. Do not open a confirmation dialog — layering a dialog on top of a drawer breaks the focus model and confuses keyboard users.

Never close on scroll. On mobile, the user's thumb may graze the scrim while scrolling the body. Guard the dismiss gesture against accidental touches — require a deliberate tap outside the panel, not any touch outside it.

Stacking drawers

Stacking drawers — opening a second drawer on top of a first — is a pattern to avoid. It creates a complex focus hierarchy, makes the escape route unclear (which Escape press closes which drawer?), and quickly runs out of screen real estate.

If stacking is unavoidable

If a workflow genuinely requires it — a detail panel that reveals a sub-edit panel — follow these rules:

  • The second drawer overlaps the first completely. Peeking the first drawer's edge behind the second creates an ambiguous layering that keyboard users cannot navigate.
  • Escape closes the topmost drawer only. The previous drawer must remain open and focussed when the second one closes.
  • Limit to two levels. Three or more nested drawers means the information architecture needs rethinking, not a third drawer.
  • Keep the second drawer narrower than the first if both are right-edge — this signals hierarchy visually even though they are stacked.

Accessibility

A drawer is a dialog variant. It carries all the same ARIA obligations as a modal dialog.

Role and attributes

  • 4.1.2The drawer panel carries role="dialog" and aria-modal="true". Without aria-modal, some screen readers continue to read the page behind the scrim as if it were accessible. high risk
  • 4.1.2The panel also carries aria-labelledby pointing to the drawer title's id, so the screen reader announces the drawer name on open. high risk
  • 4.1.2If the drawer contains a description below the title, point aria-describedby at it so assistive technology can announce the purpose.

Focus management

  • 2.4.3On open, focus moves to the first focusable element inside the panel — usually the close button or the first form field. Never leave focus on the trigger behind the scrim. high risk
  • 2.1.2Focus is trapped inside the drawer while it is open. Tab and Shift+Tab cycle through the panel's focusable elements without escaping to the page behind. high risk
  • 2.4.3On close, focus returns to the element that triggered the drawer — usually the button that opened it. If that element is gone (e.g. a deleted row), move focus to the nearest sensible element.

Keyboard

  • 2.1.1Escape closes the drawer from any focused element inside it.
  • 2.1.1Tab / Shift+Tab move through interactive elements. The cycle wraps at the last and first focusable element.

Scrim and page

  • 1.3.1Content behind the scrim must not be reachable by keyboard or screen reader while the drawer is open. Set aria-hidden="true" on the main page content, or use the native <dialog> element which handles this automatically in modern browsers.
  • 1.4.3The title and all body text must reach 4.5:1 against the panel background.

Implementation checklist

  • Panel: role="dialog" aria-modal="true" aria-labelledby="[title-id]"
  • Move focus into the panel on open
  • Trap Tab/Shift+Tab inside the panel
  • Close on Escape, scrim click, close button, and footer cancel
  • Return focus to the trigger on close
  • Set aria-hidden="true" on the underlying page while the drawer is open
