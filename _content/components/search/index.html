A text field with a search icon, clear button, and optional results dropdown — the entry point for finding content within a page, section, or entire product.

Overview

Search combines a text input with inline controls and optional live results. It is a single, composable component: the icon and input are always present; the clear button appears once there is a value; the results dropdown and scope indicator are optional additions depending on what the search covers.

Guidelines

When to use

Search is not the same as filter, and neither is the same as query. Understanding which one to reach for prevents building the wrong control.

Use caseControlWhy
Finding content anywhere in the product — orders, products, customersGlobal searchOne field with broad scope; results group by type
Finding items within a specific list or table already on the pageContextual searchFilters the visible set in real time; no network request needed
Narrowing results by category, price, date, or statusFilter barStructured facets for structured attributes; search is too open-ended
Looking up a specific record by ID or exact nameSearch with submitPrecise lookup does not benefit from instant results

Use search to find an item across the whole catalogue.

Do use search when the user is looking for something whose location they don't know.

The user is really choosing from a fixed set of categories.

Don't use search when the user is selecting from a known list — use a Select or filter control instead.

Instant vs submitted search

Instant search (results appear as you type) is better for product catalogues, people directories, and tag selectors where the user may not know the exact term. Submitted search (results appear after pressing Enter or a Search button) is better for full-text document search, order lookups, and anything that runs a slow or expensive query. Instant search needs debounce — 200–300ms after the last keystroke — to avoid a request per character. Showing a loading indicator during the request keeps the user informed while they continue typing.

Scope

Scope defines what the search looks through. If a single search field could return products, orders, and customers all at once, a scope label explains what is actually being searched and a scope selector lets the user narrow it.

The scope selector attaches to the leading edge of the search field as a button that opens a menu.

Scope patternWhen to use
No scope indicatorSearch covers a single, obvious content type — "Search products" on a product listing page
Static scope labelSearch covers one type but the page could be confused with another — a label such as "Customers" clarifies
Scope selectorThe user can choose between two or more content types — Orders, Products, Customers — from within the same search field

Empty search

When the search field is empty and focused, do not show an empty results dropdown. Either show nothing (the dropdown appears only when there are results), show recent or popular searches, or show shortcuts to common destinations. Showing an empty, loading, or "no results" state before the user has typed anything creates confusion about what went wrong.

Anatomy

Anatomy

  • 1 Search icon — non-interactive, 16px, tertiary colour
  • 2 Input field — type="search", flex-fills the container
  • 3 Clear button — appears only when the field has a value
  • 4 Results dropdown — optional, attached below the field
  • 5 Scope indicator — optional, leads the field as a selector button

Search icon

The magnifying glass icon is purely decorative — it does not trigger anything. It takes aria-hidden="true". Its job is to signal "this is a search field" before the user reads the placeholder. It stays visible in all states, including while the user is typing and after results appear.

Input field

Use type="search" rather than type="text". On iOS and Android, this provides a return-key label of "Search" and may show OS-level search history. On desktop, some browsers add their own clear button to type="search" inputs — suppress it with ::-webkit-search-cancel-button { display: none } and use the system's own clear button instead.

Clear button

The clear button (×) appears the moment the field has a value and disappears when it is empty. It carries aria-label="Clear search". Pressing it empties the field, hides the results dropdown, and moves focus back to the text input so the user can type a new query without clicking.

The native browser clear button for type="search" is hidden — only the design system's clear button is shown, so the behaviour and appearance are consistent across browsers.

Results dropdown

The dropdown attaches below the field and shares its width. It is a popover with role="listbox". Each result is an option element with a unique id. The dropdown opens when there are results and closes when: the user selects a result, presses Escape, clicks outside, or clears the field.

Results are grouped when the search covers multiple content types. Each group has a heading row (non-interactive, role="presentation") above its results. Limit the total results to around 8 — more than that does not help the user and makes the page feel unstable as results change.

Scope indicator

When the search can be narrowed to a specific content type, a scope button leads the field. It opens a small menu listing the available scopes. The current scope is written in the button label: "Products ▾". After the user changes scope, the field clears and focuses so they can start a fresh query.

Results

Results are the content shown in the dropdown as the user types. The quality of results determines whether the search component feels helpful or frustrating — the visual structure is secondary.

No results

When a query returns nothing, show the empty state inside the dropdown: a short message confirming what was searched and an optional suggestion — "No products found for 'leddar'. Did you mean 'leather'?" Do not show "no results" before the user has finished typing — wait until after the debounce period and the request has returned empty.

Debounce

Fire the search request 250ms after the user stops typing, not on every keystroke. Below 200ms, requests race each other and results flicker. Above 400ms, the lag becomes perceptible and the interaction feels slow. The clear button appears immediately when the field has a value — it does not wait for debounce.

Keyboard interaction

Search is a combobox pattern: one input field that controls one listbox of results. The keyboard contract follows ARIA Authoring Practices for combobox.

KeyResult
Type in fieldTriggers debounced search; dropdown opens when results are available
↓ in fieldOpens the dropdown if it has results; moves focus to the first result
↑ ↓ in resultsMoves focus between result items; wraps at top and bottom
Enter on a resultNavigates to the result's destination or fills the field with the result's text, then closes the dropdown
Enter in the fieldSubmits the current query; on instant-search, navigates to the highlighted result or a full results page
EscapeCloses the dropdown without selecting; focus returns to the text field; the value is preserved
Alt + ↑Closes the dropdown without selecting (alternative to Escape)
TabCloses the dropdown and moves focus to the next focusable element on the page; the value is preserved
Ctrl + A in fieldSelects all text in the field (standard browser behaviour)

Result items inside the dropdown are not focusable in the traditional sense — they use aria-activedescendant on the input to announce the active item, while visual focus styling is applied to the item itself. This keeps keyboard focus inside the field at all times, which means screen reader virtual cursor mode still works correctly.

Accessibility

Search is a combobox: one input controls one output list. The ARIA pattern is well-defined and must be implemented in full — a partial implementation produces worse results than no ARIA at all, because partial roles confuse assistive technologies.

Combobox roles

  • 4.1.2The input carries role="combobox", aria-autocomplete="list", aria-controls="[results-id]", and aria-expanded="true" when the dropdown is open. high risk
  • 4.1.2The results dropdown has role="listbox" and an id matching the input's aria-controls. Each result is role="option" with a unique id. high risk
  • 4.1.2The active result (highlighted by arrow key) is referenced from the input with aria-activedescendant="[result-id]". This is updated on each arrow key press.
  • 1.3.1Group headings in the dropdown use role="group" with aria-label set to the group name ("Products"). The heading element itself is role="presentation" to avoid double-announcing.

Live announcements

  • 4.1.3A visually hidden live region announces the result count when the dropdown opens or updates: "3 results available." Use role="status" with aria-live="polite". Do not repeat the full result list — only the count.
  • 4.1.3When no results are found, the same region announces "No results for [query]."
  • 4.1.3Do not announce on every keystroke — announce once, after the debounce delay and the results have settled.

Clear button and labelling

  • 1.1.1The clear button has aria-label="Clear search". The × glyph is aria-hidden="true". high risk
  • 2.4.6The search field has a visible <label> or a container element that serves as its label, associated with aria-label or aria-labelledby. A placeholder alone is not a label.
  • 4.1.2The scope button (when present) announces its current value: "Scope: Products".

Keyboard

  • 2.1.1All search interactions are available by keyboard, including navigating results and selecting one. high risk
  • 2.1.2Focus never becomes trapped in the dropdown — Escape always closes it and returns focus to the field.
