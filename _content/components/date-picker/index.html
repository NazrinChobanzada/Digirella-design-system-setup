A calendar control for picking single dates, date ranges, or pre-set reporting windows — use it when the user needs to see context around a date, not just type one.

Overview

DatePicker gives a text field a calendar popover. The field is always the primary input — the calendar is an assist for when the user needs to browse rather than recall. The popover opens on an explicit button press, never on focus, so it does not interrupt people who type.

Guidelines

When to use

The central question is whether the user already knows the date. If they do, a calendar is in the way — three labelled boxes for day, month and year are faster. The calendar earns its keep when the date depends on context: what weekday it falls on, how far it is from today, or what else is already booked.

Do offer a calendar for dates the user has to work out rather than recall.
Don't use a calendar for a date of birth — scrolling back 30 years is slower than typing six digits.

Single date vs date range

Use a single DatePicker when one date is the answer. Use a range picker when the span itself is the answer — a hotel stay, a reporting period, a leave request. Do not ask for two separate dates and let the user figure out the span: if it matters that they are connected, show the connection.

A range picker that shows both months simultaneously on desktop reduces navigation clicks for spans that cross a month boundary. On mobile, one month at a time is fine — the user can see the span in the two fields below the calendar.

Date formats

Date formats cause data loss when they are wrong. Store one format in the database, display a different format for the user, and never let the two leak into each other.

Never store a locale-formatted string in the database. "15/10/2026" is a display string, not a date. One day a different locale will read it as October 15 instead of the 15th of October, and the data becomes untrustworthy. Store 2026-10-15, always.

The field's placeholder should show the format: DD/MM/YYYY. The hint text below the field should show a concrete example: For example, 15 10 2026. A mask with slashes that appear as the user types is helpful for DD/MM/YYYY; it is a burden for formats that are less regular.

Week start

The first column of the calendar is locale-driven. Monday is correct for Azerbaijan, Turkey, and most of Europe. Sunday is correct for the US and some other markets. This is not a user preference — it is a locale setting. An Azerbaijani user who gets a Sunday-first calendar loses the weekend-as-a-block visual that the layout is built to provide.

Parsing tolerance

Accept the formats users actually type — not just the format shown in the placeholder. "7 oct", "07.10.2026", "7102026" and "7/10/2026" are all the same date. Normalise to the display format on blur, after the user leaves the field, not on each keystroke.

Input trigger

The text field and calendar icon form a single unit. The icon button is labelled aria-label="Open calendar" and sits inside the input's visual container at the trailing edge. It opens the popover; pressing it again or pressing Escape closes it. Focusing the text field does not open the popover — that prevents the calendar from interrupting keyboard-first users who intend to type.

Calendar popover

The popover is positioned below the trigger using the same elevation as other popovers in the system — it sits above form content. On viewports narrower than 360px, it uses a bottom sheet instead. The calendar remembers its position on re-open: if the user paged to November before closing, November opens next time.

Today vs selected

Today's date is never rendered the same way as the selected date. Today shows a ring outline to say "this is where you are in time". The selected date shows a filled circle to say "this is the date you chose". They can coincide — if the user selects today, the cell shows the fill and the ring is implied but hidden. They are different things.

Date range variant

The range picker uses two text fields and one calendar popover. The first click sets the start; the second click sets the end. Between the first and second clicks, hovering over any day previews the span. Desktop layouts show two consecutive months side by side — the span is visible across one or both panels without paging.

The calendar popover must be fully operable without a pointer. Every key listed below is required, not optional — a DatePicker that cannot be navigated by keyboard fails WCAG 2.1.1.

Disabled days are skipped when navigating with arrow keys — focus jumps over them. They are still present in the grid and announced by screen readers when the cursor would land on them; they are just not actionable.

Typing

The text field always accepts typing directly. Typing a date and pressing Tab validates and normalises it to the display format. The calendar icon stays visible alongside the typed value. If the user types an invalid date and blurs the field, an inline error appears below — the calendar icon does not change.

Constraints

Constraints narrow which dates can be selected. The three kinds are: a minimum date (nothing before), a maximum date (nothing after), and a set of disabled individual dates or ranges (fully booked days, past dates, weekends). All three apply to both clicking in the calendar and typing in the field — a disabled date typed by hand gets the same error message as one clicked.

Accessibility

The calendar popover is the most complex interactive pattern in this system. It requires a specific ARIA role structure and a full keyboard contract — both are non-negotiable.

Roles and structure

  • 4.1.2The calendar popover uses role="dialog" with aria-label="Choose date" or aria-labelledby pointing to the month heading. high risk
  • 4.1.2The day grid uses role="grid". Rows use role="row". Day cells use role="gridcell".
  • 1.3.1Day column headers (Mo, Tu, …) use role="columnheader" with abbr set to the full name: "Monday", "Tuesday". high risk
  • 4.1.2The currently focused day gets tabindex="0"; all other day cells get tabindex="-1". The rest of the calendar is reachable by Tab.

State

  • 4.1.2aria-selected="true" on the selected day cell. For a range, both the start and end cells are aria-selected="true".
  • 1.3.1aria-current="date" on today's cell. This is a different state from selection and must not conflict with it.
  • 4.1.2Disabled days use aria-disabled="true" on the button element, not the HTML disabled attribute — the keyboard must be able to move past them. high risk
  • 4.1.3A live region announces month changes when the user navigates to a different month. The month heading element carries aria-live="polite".

Keyboard

  • 2.1.1All interactions — opening, navigating, selecting, closing — are available from the keyboard alone (see Keyboard section above). high risk
  • 2.1.2Focus never becomes trapped in the calendar popover — Escape always closes it and returns focus to the trigger.
  • 2.4.3When the popover opens, focus moves to the selected date or to today. When it closes, focus returns to the calendar icon button.

Touch and size

  • 2.5.8Day cells are at least 32 × 32px. The calendar icon has a touch target of at least 24 × 24px.
  • 1.4.10On narrow viewports, the calendar popover becomes a bottom sheet and never overflows the viewport horizontally.
