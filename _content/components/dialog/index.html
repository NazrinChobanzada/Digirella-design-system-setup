Focus trapping, Escape to close, click-the-scrim to dismiss, and focus returning to the trigger — all of it works. Open one and keep pressing Tab.

Confirmation

The most common and most over-used dialog. Before writing one, ask whether the action can simply be undone instead — an undo toast is cheaper for everyone and does not punish correct clicks to protect against rare wrong ones.

Publish this listing?
It becomes visible to buyers immediately and you'll be charged the 12 ₼ listing fee.
TitleAsk the question the buttons answer. "Publish this listing?" pairs with "Publish".
BodyState what will actually happen, including cost and visibility. Never repeat the title as a sentence.
ButtonsName the outcomes — "Publish" and "Not yet". "Yes" and "No" force the user back to the title to work out which is which.
Skip itIf the action is reversible, do it and offer undo. Reserve confirmations for the genuinely irreversible.

Destructive

Delete 2 listings?
24 watchers will be notified. Deleted listings can't be restored.
CountRepeat the scope in both title and button. A bulk delete that says only "Delete" is how people destroy 200 rows meaning to destroy two.
FocusLands on the safe action. Enter should never fire the destructive button.
ConsequenceName the side effects the user cannot see — notifications sent, refunds triggered, links broken.
Typed confirmationOnly for the truly catastrophic — deleting an account. Requiring someone to type "DELETE" for one listing trains them to type it without reading.

Form dialog

A short task inside the modal. Legitimate up to about six fields; past that it belongs on a page with a URL, a back button and room to breathe.

Opening & closing

TriggerResult
EscCloses. Always, with no exception — including destructive dialogs, where closing is the safe outcome.
Click scrimCloses a confirmation. Does not close a form with unsaved changes — it asks first.
Cancel buttonCloses and discards. Always present; a dialog with only one way out is a trap.
Primary actionCloses on success. Stays open on failure, with the error inside the dialog.
Browser backCloses the dialog rather than leaving the page. On mobile this is the gesture users reach for first.
MotionScrim fades and the container rises 8px over --duration-slow (360ms). Exit is faster — 220ms — because leaving should not feel laboured.
Never auto-openA modal that appears without a user action — on page load, on a timer — is an interruption nobody asked for.

Focus & keyboard

On openFocus moves into the dialog: the first field in a form, the safe action in a confirmation. Never the destructive button.
TrapTab cycles inside the dialog only. This is the one place in the system where a focus trap is correct — the page behind is genuinely inert.
On closeFocus returns to the element that opened the dialog. Losing focus to the top of the page is the single most common modal bug.
EnterSubmits the form dialog. In a confirmation it fires the safe action, matching where focus landed.
BackgroundThe page behind gets inert or aria-hidden, so screen readers cannot wander out of the dialog.

Scrolling & mobile

Body scrollsOnly the dialog body scrolls. Header and action row stay pinned, so the commit action is never below the fold.
Page lockedThe page behind does not scroll, and does not jump when the scrollbar is removed.
MobileFull screen below 600px. Actions pin to the bottom, stacked full width with primary on top.
KeyboardWhen the on-screen keyboard opens, the focused field stays visible and the action row rides above the keyboard rather than under it.

Stacking

One modal at a time. A dialog opening from a dialog means the first task was not short enough to be a dialog.

ExceptionA destructive confirmation over a form dialog, when closing the form would lose work. It is the only legitimate second layer, and it never gets a third.
ToastsAppear above the scrim, so a background success does not vanish unseen.
MenusMenus and popovers inside a dialog render above it but stay within its focus trap.

Best practices

Do
Cancel this order?
Your refund arrives in 3–5 business days.

Title names the action, buttons name the outcomes. Readable without the body text.

Don't
Are you sure?
This action cannot be undone.

"Are you sure?" and "Yes/No" describe nothing. The user must reconstruct what they clicked a moment ago.

One decisionA dialog asks one question. Two questions in one modal means neither gets read.
No nestingNo tabs, no accordions, no wizards inside a modal. Those are all signals it should be a page.
Preserve inputNever clear fields on error, and never lose them on accidental dismissal.
FrequencyIf users see the same dialog many times a day, remove it. A confirmation people click reflexively protects nobody.

Accessibility

Rolerole="dialog" with aria-modal="true", plus aria-labelledby pointing at the title and aria-describedby at the body.
Focus trapRequired. Tab and Shift+Tab cycle within the dialog; nothing behind the scrim is reachable.
Return focusOn close, focus goes back to the trigger. Without this, keyboard users restart from the top of the page every time.
EscAlways closes, on every dialog. WCAG 2.1.2 — no keyboard trap without an escape.
Inert backgroundinert on the page root, so assistive tech cannot read content the sighted user cannot reach.
AnnounceErrors appearing inside the dialog go in a live region, or they are silent to screen-reader users.
ScrimDecorative and aria-hidden. It must never be the only way to close — Esc and a Cancel button always exist.
