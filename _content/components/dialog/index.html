A Dialog interrupts the current task to request a decision or display information that requires the user's full attention before they can continue.

Overview

Dialogs block interaction with the rest of the page until dismissed. They centre over a darkened scrim, signal urgency, and demand a response — which is exactly why they should be used sparingly. Every dialog carries a cost: it stops flow, forces a decision, and can frustrate someone who was in the middle of something else.

The system provides four sizes. All share the same structure — scrim, container, header with title and close button, scrollable body, footer with actions — and the same motion: 200ms fade on the scrim, a subtle scale-in on the card.

Guidelines

When to use

A dialog is the right choice when the task cannot safely continue until the user responds. It is the wrong choice when you want attention but can live without it.

Content guidelines

Title

The title names the action or the question — not the component. "Delete listing?" is a title. "Confirmation" is not. Keep it to one line; if it wraps, the content has drifted into body territory.

Remove card ending 4242?

You'll need to add a new card before your next order.

The title states exactly what's about to happen — the user can answer the question without reading the body.

Are you sure?

This action cannot be undone.

"Are you sure?" could apply to any action. The user still has to read the body to know what they're confirming.

Body

Explain the consequence, not the action. "This will remove your listing from all search results" is useful. "You are about to delete a listing" describes what the button does, which the title already said. Keep it to two or three sentences. If you need more, the decision is too complex for a dialog.

Actions

Two actions in almost all cases. The primary action goes on the right; Cancel or a dismissal goes on the left. Match the action label to the title verb: if the title says "Delete listing?", the confirm button says "Delete listing" — not "Yes" or "OK".

Primary actionRight-aligned. Names the action. Uses .btn--primary, or .btn--danger for destructive actions.
CancelLeft of primary. Uses .btn--ghost. Closes the dialog without doing anything.
Three actionsRare. Only when there is a genuinely distinct third option — not "Maybe later" as an escape from making a decision.

Sizes

Four sizes cover every use case. Choosing too large a size for a two-line confirmation gives it an air of importance it doesn't deserve; choosing too small for a form cramps the fields and pushes buttons off-screen on mobile.

Behaviour

Opening and closing

Opening

A dialog opens in response to a deliberate user action — pressing a button, submitting a form that reveals a conflict. It never opens automatically on page load, on a timer, or in response to scrolling. The only exception is a session-expiry warning, and even that should warn first and open later.

On open, focus moves into the dialog — to the first focusable element if there is a logical starting point (like the primary input in a form), or to the dialog container itself if not. The scrim and card animate in simultaneously: the scrim fades from 0 to 0.4 opacity; the card scales from 0.96 to 1 and fades in, both over 200ms on --ease-standard.

Closing

Three ways to close a dialog: pressing the close button in the header, pressing Escape, or clicking the scrim. The last two are suppressed on confirmation dialogs — where a user must make an explicit choice, accidental dismissal by overshooting the cancel button or reaching for the keyboard is a real risk. On confirmation dialogs, only the Cancel button and the primary action close the dialog.

On close, focus returns to the element that triggered the dialog. This is not optional — losing track of keyboard position after a dialog closes is a common and disorienting failure.

Focus trap

While a dialog is open, Tab and Shift+Tab cycle only through focusable elements inside it. Focus does not leave the dialog to reach page content behind the scrim. This is both an accessibility requirement and a product protection: a keyboard user should not be able to interact with blocked content.

Confirmation dialogs

A confirmation dialog exists to protect against irreversible mistakes. It adds a step, which slows people down — that is its purpose. Use it only when the action genuinely cannot be undone, or when the cost of the mistake (financial, reputational, data loss) is high enough to justify the friction.

Three rules for confirmation dialogs:

  1. The confirm button uses .btn--danger. The action label repeats the title verb: "Delete listing" confirms "Delete listing?". The danger colour and the label together name the consequence twice without extra copy.
  2. The cancel button is "Keep [thing]" or a verb that undoes the title. "Cancel" is ambiguous on a dialog titled "Cancel order?" — it might mean "cancel the order" or "cancel the dialog". Use "Keep order" instead.
  3. Close on overlay and Escape are suppressed. Confirmation dialogs require an explicit choice. An accidental Escape should not silently abort a form the user spent time filling in.

Do not use a danger button for the trigger that opens the dialog. The trigger should be a secondary or ghost button — it starts the decision process, it does not complete it. The danger button inside the dialog is the one that carries the consequence.

Scrollable body

When dialog body content is taller than the available viewport height, the body scrolls independently. The header and footer are position-sticky and always visible, so the user can always see the title and can always reach the actions without scrolling to the bottom first.

The scrollable region gets a faint gradient fade at the bottom edge when scrollable content lies below the visible area, and at the top edge once scrolled. These fades do not appear in browsers or contexts that do not support them — the content remains accessible without them.

Accessibility

Dialogs touch more WCAG criteria than almost any other component. The criteria below are the ones a dialog commonly fails in production.

Role and naming

  • 4.1.2The dialog element carries role="dialog" (or use <dialog>). high risk
  • 4.1.2aria-labelledby points to the title element. Without it, a screen reader announces "dialog" with no context. high risk
  • 4.1.2aria-describedby points to the body text on confirmation dialogs, so the consequence is announced when the dialog receives focus.
  • 4.1.2Modal dialogs set aria-modal="true" to tell screen readers not to read the obscured content behind the scrim.

Focus management

  • 2.4.3On open, focus moves into the dialog. On close, focus returns to the triggering element. high risk
  • 2.1.2Tab and Shift+Tab cycle only through interactive elements inside the dialog (focus trap). high risk
  • 2.1.1Escape closes the dialog (except confirmation dialogs, where Escape must not dismiss silently).

What you still have to do

  • Wire aria-labelledby to the dialog title's id.
  • Implement the focus trap in JavaScript — the browser's native <dialog> provides this when showModal() is used, but a custom implementation must build it.
  • Restore focus to the trigger element on close.
  • Suppress Escape on confirmation dialogs and add a keyboard-accessible alternative (the Cancel button).
