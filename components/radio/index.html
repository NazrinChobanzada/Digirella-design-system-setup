Radio New

Radio buttons let people choose exactly one option from a small set of mutually exclusive choices.

Overview

Where a checkbox lets someone pick any combination, a radio group enforces a single selection — choosing one deselects the others. That makes radio buttons right for questions with one correct answer: a shipping speed, a payment method, a plan tier. Because all options are visible at once and selecting one immediately clears the previous choice, the list should always be short and complete.

Guidelines

When to use

Radio buttons are best when the choice is between two to seven fixed, mutually exclusive options, and when seeing all options at once helps the person decide. For more options, a Select is more appropriate. For a single on/off setting, use a Switch. For multiple independent selections, use Checkboxes.

Do use radio buttons for a plan tier — only one can apply at a time.
Don't use radio buttons for independent settings — each can be on or off simultaneously, so use Checkboxes.

Groups

A radio button is never used alone. A group of one has no selection to enforce. A group of two is the minimum — and a pair that maps naturally to on/off may be better expressed as a Switch or a single Checkbox.

Always provide a group label

Wrap every radio group in a <fieldset> with a <legend>. The legend names what the group is deciding — "Payment method", not "Options". A standalone aria-labelledby pointing to a heading above the group is acceptable, but the fieldset/legend pattern works across all assistive technologies without configuration.

Default selection

Always pre-select a default when one option is the most common choice or the safest starting point. An empty radio group forces the user to make a choice before they can understand the options. The pre-selected option should be the one that most users would choose — not the one that is most profitable.

Do pre-select the most common option — here, free shipping.
Don't leave the group with nothing selected — it asks a question that already has a sensible answer.

Option count

Two is the minimum. Seven is the practical maximum. Beyond that, the list becomes a scroll target and the user loses the ability to compare options at a glance. Switch to a Select dropdown at eight or more, or consider whether the options can be restructured into a smaller set of meaningful categories.

Content guidelines

Label wording

Write radio labels as concise noun phrases that name the option directly. Avoid restating the question — the group legend handles that. "Credit or debit card" is enough; "Pay by credit or debit card" repeats the group label's intent. Keep labels parallel in structure: if one option is a noun phrase, all options should be noun phrases.

Do keep labels parallel — all nouns, same grammatical pattern.
Don't mix label styles — inconsistent construction makes the group harder to scan.

Description text

Descriptions add context when the label alone is not enough to distinguish options — a pricing tier with a short description of what is included, or a shipping option with cost and timing. Keep descriptions to one sentence, and do not repeat what is already in the label.

Ordering options

Order options logically — low to high for sizes and prices, most common first for lists without a natural sequence. Never order options to steer users toward a particular choice through position alone — most people read the first option as the default recommendation.

Behaviour

Keyboard interaction

Radio groups have a specific keyboard pattern that differs from checkboxes and most other controls. The group as a whole receives focus once — on the selected option, or on the first option if nothing is selected. Within the group, arrow keys move selection rather than Tab. This keeps a radio group from consuming multiple tab stops.

Navigation model

Try it: Tab in, then use ↑ ↓ to move between options
KeyResult
TabEnters the group, focusing the selected option. If nothing is selected, focuses the first enabled option.
↓ / →Moves selection to the next enabled option. Wraps from the last to the first.
↑ / ←Moves selection to the previous enabled option. Wraps from the first to the last.
Tab (again)Leaves the group and moves to the next focusable element.
Shift+TabLeaves the group and moves to the previous focusable element.

Disabled options

Arrow key navigation skips disabled options. If all options in a group are disabled, Tab passes over the group entirely. A group with only disabled options should still be visible with a reason — removing it entirely deprives someone navigating linearly of the context that the decision was made for them.

Arrow keys move selection immediately. Unlike checkboxes, there is no separate step to confirm a radio selection — the arrow key both focuses and selects. This is intentional browser behaviour. Do not add a confirmation step inside the group; if the decision is consequential, show a summary and a Save button outside the group.

Accessibility

Radio buttons rely on their group structure for most of their accessible meaning. The individual circle is a binary widget; the group is the choice. Both need to be correctly represented.

Group structure

  • 1.3.1Wrap every radio group in a <fieldset> with a <legend>. The legend is announced before each option when navigating into the group. high risk
  • 4.1.2All buttons in a group must share the same name attribute. Without it, they are not a group and arrow-key navigation does not work. high risk
  • 3.3.2When selection is required, indicate it visibly and connect any validation error with aria-describedby on the <fieldset>.
  • 3.3.1Surface the error in text, not colour alone. "Choose a delivery method" beats a red border with no message.

Individual button

  • 1.3.1Use a native <input type="radio"> inside a <label>. The association between the input and label is programmatic and announced automatically.
  • 2.4.7A visible focus ring on the focused option, using --focus-ring.
  • 1.4.11The unselected circle border must reach 3:1 against the page background. high risk
  • 1.4.3Label and description text reach 4.5:1, including in disabled state.
  • 2.5.8Touch target padded to at least 24×24px via the label's hit area.

Keyboard

  • 2.1.1Arrow keys navigate and select within the group. Tab moves to the next control outside the group.
  • 2.1.1Do not trap focus inside a radio group. Tab and Shift+Tab must leave it. high risk
  • 2.4.3Focus order follows reading order — top to bottom for a vertical list, left to right for a horizontal one.

What you still have to do

  • Wrap every radio group in a <fieldset> with a <legend>.
  • Give all buttons in a group the same name attribute.
  • Pre-select a default option so the group is never blank before a form submit.
  • Connect validation errors to the group with aria-describedby on the fieldset.
