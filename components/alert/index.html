Components

Alert New

A short message about a condition — where it sits decides its scope, lifetime and dismissal. Severity is a separate axis from placement, and it carries meaning, not emphasis.

Overview

An alert is inline and persistent — it lives in the page, not over it, and it does not vanish on its own. The single most important decision is where to put it: distance between the message and its cause is what makes alerts get missed.

Placement decides almost everything about an alert: scope, lifetime, whether it can be dismissed, and how a screen reader hears it. Severity is independent — it answers "what kind of thing is this?", not "how loud should it be?".

Guidelines

Principles

Put the message where the problem is

A field error belongs under the field, a section problem inside the section, a service-wide problem at the top of the page. Distance between the message and its cause is what makes people miss it.

field → section → page

Severity is meaning, not emphasis

Red means something is broken or blocked — not "this is important". A warning dressed as an error teaches people to ignore red.

error ≠ loud · info ≠ quiet

Say what to do next

Every message that reports a problem names the action: retry, fix a field, contact someone, wait. A message with no next step is noise with an icon.

"Card declined. Try another card."

Never interrupt for something routine

Saves, copies and small confirmations are toasts at most. If the user must read it to continue, it is not a toast — and if they must act on it immediately, it is a dialog.

routine → toast · blocking → dialog

Placement

Same component, four positions. The position is the real variant — it decides scope, lifetime, dismissal and live-region role.

Inline

Immediately above or below the element it concerns, inside the form flow. Never dismissible: disappears when the condition clears.

scope: one control · tied with aria-describedby

Section

Below the section heading, above section content. The message belongs to that card, panel, or step and scrolls with it.

scope: one panel or step · dismissible when advisory

Page

Top of page content, between navigation and the h1. One at a time — if two conditions apply, write one combined message.

scope: this screen · one maximum

Toast

Floating, transient, non-blocking. Confirms an action the user just took. Auto-dismisses; the only placement with a timer. Never takes focus.

scope: last action · timer pauses on hover/focus

Variants

Severity

Severity is the second axis, independent of placement. It answers one question: what kind of thing is this? Colour, icon, and words all carry it — colour never alone.

SeverityMeansDismissible?
InfoContext or a neutral change of state the user didn't causeYes
SuccessA process completed and left a lasting positive state — verified identity, activated featureYes, or auto as a toast
WarningNothing is broken yet, but something will go wrong or has a consequence the user can addressUsually
DangerSomething failed or is blocked. The user cannot continue as intendedNo, while the condition holds

Anatomy

1 ⚠
2 Shop suspension warning
3 Your listing count exceeded the free tier limit. 4Upgrade your plan to keep all listings active.
  1. 1
    Icon — 18–20px, colour-matched to the severity token. Always present and always aria-hidden="true".
  2. 2
    Title — Optional. Sentence case, no period, five words or fewer. Recommended when the body is more than one sentence.
  3. 3
    Body — Always required. What happened, then what to do next. One or two sentences.
  4. 4
    Action — Optional. One specific link or quiet button. Named for what happens — "Update card", not "Click here".
  5. 5
    Dismiss — Optional. Top-right, 24×24 target minimum. aria-label names the alert — "Dismiss shop suspension warning".

Content guidelines

Title says the state, not the severity"Payment failed", "Action required" — not "Warning:" or "Error:". The icon and colour already say that.
Body: what + what nextOne or two sentences. "Your card was declined by your bank. Try a different card or contact your bank." — not just "Your card was declined."
One action maximumIf two things need doing, the body should explain the order and link to the first. A second action belongs on the page, not in the message.
No error codes in the body"Your card was declined" is useful. "Error 402: payment_failed" is not. Technical codes belong in a collapsible detail or a log.
Never repeat the variant nameDon't start the title with "Warning:" or "Error:" — the icon already communicates this to everyone, including screen-reader users, when the live region text leads with the severity word.
Screen reader text leads with severityWhen injected dynamically, the announced text should start with "Error:", "Warning:" etc. so screen-reader users hear the kind before the detail.

Behaviour

Dismissible vs persistent

Most alerts should be persistent — they stay until the condition is resolved, not until the user hides them. A user who dismisses a "payment failed" alert has not fixed the payment.

Allow dismissalFor informational and advisory alerts where the user may already know — a feature announcement, an upgrade prompt, a contextual tip
Prevent dismissalOn danger and warning alerts that block a workflow. If the account is suspended, hiding the message creates a worse experience than leaving it
Remember dismissalsStore the dismissed state so the announcement does not reappear on the next visit. An announcement seen and closed should stay gone

Appearing & leaving

MomentRule
On page loadRender with the page, in the layout. Nothing animates in on first paint — content that shifts after the user starts reading is a layout bug
After an actionInsert in place and push content down rather than overlay it. A message that covers what the user just read is a modal in disguise
EnteringFade + 4–6px rise, 120–180ms. Toasts slide from their corner. Nothing bounces
LeavingFade out 100–150ms, then collapse the space. Collapsing first makes the page jump under the user's pointer
On condition resolvedAn alert about a condition disappears when the condition clears — no extra success message on top, no dismissal needed
On navigationPage and section alerts die with the page. Toasts finish their timer or are dropped — never carried to the next screen
Reduced motionAppear and disappear instantly. The timer and pause behaviour for toasts remain exactly the same

Stacking

One page alertTwo stacked page banners means neither gets read. If two conditions apply, write a single message that addresses both
Toasts: three visible maximumNewest nearest the corner. Beyond three, queue the rest — a tower of toasts covers the UI they're about
Order: severity first, then ageIf two must coexist, the more severe message sits on top
Collapse repeats"3 uploads failed", not three identical toasts. The same trigger updates the existing toast and restarts its timer rather than stacking a duplicate
Page + inline allowedTheir scopes differ: the page-level problem at the top, the specific field that caused it marked below. Two page alerts for the same event are not allowed

Accessibility

Live regions

  • 4.1.3Use role="alert" (assertive) for danger and warning alerts injected after a user action; use role="status" (polite) for info and success. high risk
  • 4.1.3The live-region container must exist in the DOM before the message is injected. Creating container and message together announces nothing. high risk
  • 4.1.3Never display:none a live-region container — hidden regions don't announce. Keep it present and visually empty when there is no message.
  • 4.1.3Alerts rendered with the initial page load need no live region — they are already in document order.
  • 4.1.3Use one live-region container per placement scope. Multiple assertive regions firing together garble each other.

Colour and icons

  • 1.4.1Severity is never colour alone. The icon shape and the first word of the message carry it too — "Error: payment declined" reads the same in greyscale as it does in colour.
  • 1.4.3Message text reaches 4.5:1 on its tinted background — tinted backgrounds are where this quietly fails.
  • 1.4.11The icon and the left border reach 3:1 against the surrounding surface.
  • 1.3.1The icon carries aria-hidden="true" — severity is communicated through the live region's lead word and the surrounding text, not through the icon.

Focus

  • 3.2.2An alert appearing after an action never moves focus unless it is a success banner on a newly loaded page — the one accepted exception, because the page itself changed.
  • 2.1.1Actions and the dismiss control are reachable by keyboard, in reading order.
  • 2.4.3After dismissal, focus moves to a logical nearby element — the next focusable item or the element focused before the alert appeared. Never to body.
  • 2.5.8The dismiss button is a 24×24 target minimum, separate from the action link.

What you still have to do

  • Add role="alert" or role="status" to dynamically injected alerts, and make sure the container element exists in the DOM before the message is written into it.
  • Give the dismiss button a descriptive aria-label that includes the subject: "Dismiss shop suspension warning", not just "Close".
  • Start the announced text with the severity word — "Error: …", "Warning: …" — so screen-reader users hear the kind before the detail.
  • Store dismissals persistently so the same announcement does not reappear on the next visit.
