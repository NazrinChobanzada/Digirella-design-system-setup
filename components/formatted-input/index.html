Components

Formatted input New

Fields whose answer has a shape: an email address, a password, a phone number, a card. The format is known before anyone types, so the field should say so.

Overview

A formatted input is a text input that knows something about its answer. That knowledge buys three things a plain field cannot offer: the right keyboard on a phone, autofill from the browser, and a hint that states the shape before the first keystroke rather than after the first mistake.

We only use this for order updates.
Mobile number, for delivery updates.

Both placeholders show the shape of the answer rather than repeating the label.

Guidelines

Principles

Three ideas separate a formatted field from a plain one.

State the format before it is needed

If a field will reject an answer for its shape, that shape belongs in the hint, visible from the start. Discovering a password rule after failing it is the most avoidable error in any sign-up flow, and it is the one people abandon over.

The format goes in the hint, not the placeholder

A placeholder disappears on the first keystroke, so anything the person still needs while typing cannot live there. The format is exactly that: someone checks it halfway through a card number, not before they start.

So the hint carries the shape, visibly, for as long as the field is on screen. The placeholder stays a plain example — or stays empty. It is a nice-to-have that vanishes, and nothing important should depend on it.

The rule stays visible; the placeholder only illustrates it.
The rule leaves exactly when it is needed.
Keep placeholders plain. "Enter…", "Select…", "Type here…" repeat what the control already communicates, and a placeholder that reads like an instruction competes with the hint that actually holds one. Show a bare example, or leave it empty.

Accept what people actually type

People paste phone numbers with spaces, card numbers with dashes, and email addresses with a trailing space. Strip and normalise on the way in rather than rejecting. A field that refuses a pasted value because of a space is technically correct and practically broken.

When not to use a formatted input

Reach for a plain Text input when the answer has no fixed shape, and Number input when it is a quantity you will do arithmetic on. A postcode or a card number looks numeric but is a digit string — it keeps leading zeros and never needs a stepper, so it belongs here rather than there.

Do not use a formatted input to enforce a business rule that may change. Shape belongs in the field; policy belongs in validation you can update without a release.

Dates and times

A date is a formatted value, so the typed part of a date field follows every rule on this page: the format in the hint, an inputmode, an autocomplete token, permissive parsing. But a date picker is not only a field — it adds a calendar overlay with its own grid, keyboard model and focus management, and that machinery is larger than the field it sits under.

So they are separate components. DatePicker and TimePicker own the overlay; this page owns the field beneath it. Build the typed field first and make it work on its own — someone who knows the date will always type it faster than they can navigate a calendar, and a picker whose field cannot be typed into is a picker that slows down the people who need it least.

Variants and style

Variants

The variant is the combination of type, inputmode and autocomplete. It changes almost nothing visually and a great deal functionally.

Affixes

A prefix or suffix sits inside the field boundary, so the pair reads as one control rather than a field with something stuck beside it. Use them for the fixed part of a format — a currency symbol, a country code, a domain — never for the label. In this locale the currency symbol follows the number, so prices take a suffix.

The affix is not focusable and carries no meaning of its own — it repeats what the label already established, so a screen reader hearing only the label loses nothing.

Masking

Masking inserts the separators as someone types: spaces into a card number, a dash into a date. It helps when the grouping is genuinely standard and hurts the moment it fights the person.

  • Never move the cursor unexpectedly. A mask that jumps the caret after a paste is worse than no mask.
  • Never block characters silently. If a letter is not allowed, ignore it — do not clear the field.
  • Always allow paste, and normalise what arrives.
  • Keep the underlying value unmasked. Submit digits, display grouping.

Password

Passwords carry two rules the other formats do not.

A visibility toggle, always

Typing a long password blind on a phone is the main reason people pick short ones. NIST SP 800-63B recommends offering the option to display the password while it is being entered, for exactly this reason.

The toggle is an eye icon inside the field — no text, so it does not compete with the value. It carries aria-pressed and an aria-label that changes with its state: "Show password" becomes "Hide password" once revealed.

At least 10 characters, including a number.

Rules before entry, not after failure

The requirements go in the hint and stay visible while typing. Revealing them only in an error message means the person has already lost the attempt.

Why paste stays enabled

Blocking paste feels safer and measures worse, and the guidance is explicit about it. NIST SP 800-63B states that verifiers shall allow password managers and autofill, and should permit paste so managers can be used where autofill APIs are unavailable — noting that password managers have been shown to increase the likelihood of people choosing stronger passwords. The UK NCSC reached the same conclusion in its guidance on letting people paste passwords.

The mechanism is straightforward. A person who cannot paste cannot practically use a generated 24-character password, so they choose one they can type from memory — which means shorter, reused across sites, and guessable. Blocking paste does not stop an attacker, who is not typing into your form at all; it only constrains the person defending the account.

The concern behind the instinct is real but sits elsewhere: clipboard contents can be read by other software on a compromised device. That is a threat to the device, not something a form can fix, and the mitigation is a password manager with a clearing clipboard — not a field that refuses paste.

Use autocomplete="new-password" on sign-up and current-password on sign-in. These tell a password manager which field is which. Disabling autocomplete on a password field has the same effect as blocking paste, for the same reason.

Behaviour

Validation

Validate on blur, and once a field has erred switch it to validating on input so the message clears the moment it is fixed. Be permissive about shape and strict about meaning: accept a phone number however it is spaced, then check it resolves.

Add everything after the @ sign.
This card number is one digit short.

Name what is wrong with this value where you can. "One digit short" is worth more than "Invalid card number", and it costs one comparison to work out.

Async checks

When a field has to ask a server — an availability check, an address lookup — show the wait inside the field rather than disabling it. The person can keep typing; the answer arrives when it arrives.

Checking availability
✓
Available

Never block submission on a check that has not returned. Let the form submit and resolve the conflict server-side — a spinner that never resolves should not be able to trap someone in a form.

Accessibility

Formatted fields carry everything a text input does, plus the criteria below. Items marked high risk are the ones that come up most often in review.

Format and autofill

The criteria that exist because the field knows its answer.

  • 1.3.5An autocomplete token on every field collecting the person's own data. This is the difference between a checkout that takes one tap and one that takes forty. high risk
  • 3.3.2The format is stated before entry, in the hint. A rule revealed only on failure fails this. high risk
  • 3.3.3The error names the correction where one can be worked out, not just that the value is wrong.
  • 1.4.3Autofilled values keep their contrast — browser autofill backgrounds override yours and are a common failure.
  • 3.2.2No context change on input. A mask must not submit, navigate or move focus to the next field on its own.

Password toggle

A button inside a field, and it has to behave like one.

  • 4.1.2The toggle exposes aria-pressed, and its accessible name changes with the state. high risk
  • 2.1.1Reachable and operable by keyboard, in the tab order after the field.
  • 2.5.8At least 24 × 24px, even inside a 38px field.
  • 1.4.11The toggle is distinguishable from the field's own border at 3:1.

Sources

The paste and visibility guidance on this page is not a house preference. It follows:

  • NIST SP 800-63B, Digital Identity Guidelines — verifiers shall allow password managers and autofill, should permit paste, and should offer an option to display the password while it is entered.
  • NCSC (UK National Cyber Security Centre), Let them paste passwords — the same conclusion, with the reasoning about password manager adoption.

Record this alongside any internal security review. The rules read as counterintuitive, and without the citation someone will eventually re-introduce a paste block believing it is a hardening measure.

What you still have to do

  • Set autocomplete on every personal field. It is one attribute and the single highest-value thing on this page.
  • Put the format in the hint, not only in the placeholder — the placeholder leaves.
  • Never disable paste, and never turn off autocomplete on a password field.
  • Keep the accessible name of a visibility toggle in sync with what it will do next.
