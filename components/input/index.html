Components

Text input New

A field for short, free-form text — one line or several. The plainest control in the system, and the one most forms are mostly made of.

Overview

A text input collects an answer the system cannot predict: a title, a name, a note. It accepts anything, which is its strength when the answer really is open, and its weakness the moment the answer has a shape it has to take.

All three text fields in this system are the same element underneath. What separates them is not what they accept — it is what the system knows before anyone types, and therefore how much of the work it can do on the person's behalf.

FieldThe system knowsSo it can
Text inputNothing about the answer.Only hold what is typed. No keyboard hint, no autofill, no format to check against — every rule has to be written by you and read by them.
Formatted inputThe shape of the answer.Bring the right mobile keyboard, offer autofill from the browser, and state the format before the first keystroke.
Number inputThat the value is a quantity.Offer controls to adjust it, enforce a range, and align the digits for comparison.

So the question is not what the value looks like but what you know about it. If you know the shape, use the field that knows it too — the alternative is teaching the same rule in a hint, checking it in your own validation, and apologising for it in an error message.

Guidelines

Principles

Four ideas explain most of the decisions on this page.

The question has to stay on screen

A label is not decoration for the field, it is the question the field is asking. A placeholder cannot do that job because it leaves as soon as someone answers, which strands anyone who is interrupted, reviewing before submit, or reading the form aloud.

The field should describe its answer

The width of the field, the hint under it and the height of the box all say something about the expected answer before anyone types. A field sized for a paragraph invites a paragraph, even when you wanted three words. Getting this right prevents errors rather than catching them.

Correct late, forgive early

Nobody writes a description in one pass. Validating on every keystroke turns an unfinished answer into a failure, so the system waits for blur — and once a field has erred, it switches to validating on input, so the message clears the instant it is fixed.

An error is an instruction

"Invalid input" tells someone they have failed. "Titles need at least 10 characters" tells them what to do. The second costs the same to write and ends the interaction; the first starts a guessing game.

When not to use a text input

The pattern behind the table: a field someone has to guess the shape of is a field they will get wrong. If you know the shape, use the control that knows it too.

Variants and style

Anatomy

  • 1 Label — always visible, above the field.
  • 2 Container — 38px tall, 1px --border-control.
  • 3 Placeholder — an example, never the label.
  • 4 Hint — the rule or the reason you are asking.

Labels are not optional

Every field has a visible label. A placeholder disappears the moment someone types, taking the question with it — which is hardest on exactly the people who most need it.

The label stays; the placeholder shows an example.
The label vanishes on the first keystroke.

Affixes

A prefix or suffix sits inside the field boundary, so the pair reads as one control rather than a field with something stuck beside it. It is documented here because it belongs to the field itself — Formatted input and Number input both use the same construction.

%

An affix carries the part of the value that is not typed — a unit, a symbol, a dialling code — never the label.

Static affixes

A fixed symbol like % is decorative: it is not focusable and is hidden from assistive technology, because it repeats what the label already established. Put the unit in the label too, so it is announced once.

Selectable affixes

When the unit is part of the answer rather than a description of it, the affix becomes a control. Grams or kilograms, one country code or another — the person is choosing, not just reading, so it takes a real <select> with its own accessible name and its own place in the tab order.

The test is whether changing it changes the meaning of the number. 15% is one value; 1.4 in grams and 1.4 in kilograms are two. The second needs a control; the first does not.

Submit the pair together — the amount and its unit are one answer, and a value that arrives without its unit is worse than no value, because it looks usable.

A native <select> opens an operating-system menu that cannot be styled. The closed control is ours — border, height, type, focus halo all follow the system. The open list is not: it is drawn by iOS, Android or the desktop OS, and no CSS reaches it. That is a browser boundary, not an oversight.

Accept it where the native list is genuinely better — on a phone it is a full-height wheel with momentum scrolling, larger targets and familiar gestures that no custom menu matches. Replace it with Combobox where the open list has to look like the rest of the product, or needs search, grouping, icons or multi-select. The trade is real: a custom listbox has to rebuild typeahead, arrow-key navigation and focus trapping that the native control gives away for free.

Suffix is the default here. Units and currency follow the number in this locale — 1.4 kg, 2.480 ₼ — so a trailing affix matches how the value is read aloud. A prefix is for the rare case where the symbol genuinely leads in the data itself, such as a + before an international dialling code.

Variants

One job, two shapes.

ShapeExampleUse forDon't use for
Single line Titles, names, references — answers of a few words that will not wrap. Anything the person may want to review as a paragraph.
Multi-line Descriptions, notes, messages. Add a counter when there is a real limit. Short answers — a tall box invites a long reply you did not want.

Multi-line

A multi-line field grows rather than scrolls where the layout allows it. A field that scrolls at three lines hides the beginning of the answer from the person writing it.

Show a counter only when a limit really exists, and place it below the field on the right. A counter with no limit behind it is decoration that makes people self-conscious about length.

37 / 180

When the limit is reached, the counter turns red and further typing is refused rather than silently truncated. Never cut text on submit — losing the end of a sentence someone wrote is worse than rejecting it while they can still see it.

The label and the value share a size and are separated by weight: 500 for the question, 400 for the answer. The placeholder matches the value exactly and changes only its colour, so text does not jump in size the moment someone starts typing.

On screens under 640px the value rises to 16px. Below that, iOS Safari zooms the whole page when the field is focused — the one case where type goes up on a small screen rather than down.

Focus halo

Fields use a 3px halo of --color-primary-subtle rather than the offset ring buttons get. In a dense form an offset ring collides with neighbouring fields; a halo hugs the border and stays inside the row.

Inputs use a slightly larger radius than buttons. Buttons are objects you press; fields are containers you fill, and the softer corner reads as a space rather than a target.

Width

Match the field width to the expected answer. Width is a hint nobody has to read.

In a form, keep fields in a single column. Side-by-side fields are only for values that genuinely belong together.

Labels and messages

Two rules hold in any language: name what you are asking for, and say what to do when it goes wrong. "Titles need at least 10 characters" and "Başlıq ən azı 10 simvol olmalıdır" are the same instruction; "Invalid input" and "Yanlış" are the same failure.

Required and optional

Mark required fields with an asterisk after the label, and explain it once at the top of the form. Optional fields carry no mark — adding "optional" to everything else doubles the noise to say the same thing.

* Required fields

The asterisk is aria-hidden and the field carries aria-required="true". Drawing the mark and announcing the fact are two separate jobs: the asterisk is a visual convention that means nothing to a screen reader, and aria-required is announced but invisible. Both are needed, and neither substitutes for the other.

Error messages

Say what is wrong and what to do. The message replaces the hint and is wired through aria-describedby, so a screen reader reads it as part of the field.

Titles need at least 10 characters.
Names the rule, so the fix is obvious.
Invalid input
Restates that something is wrong without saying what.

Colour is never the only signal. The red border is paired with an icon and a message, so the error survives a monochrome screen or colour-blind vision.

Casing and word order are language decisions, not system decisions. Turkish and Azerbaijani put the verb last, and capitalisation conventions differ. Set those rules once per locale in your content guidelines; the system only asks that labels are specific and messages are actionable.

Skeleton

The error field shows the whole treatment together: red border, focus halo, status icon, message, and a clear button so the value can be discarded in one action rather than selected and deleted.

Read-only versus disabled

Read-only means "applicable but fixed" — an order number, a seller code. It stays in the tab order, stays selectable, and passes contrast, so it can be read aloud and copied. Disabled means "not applicable at all": it leaves the tab order, is skipped by screen readers, and is exempt from contrast.

Reach for read-only more often than you think. A value someone cannot change is still a value they need to see.

Skeleton

Use a skeleton on initial page load, when the field exists but its value has not arrived. Match the skeleton to the shape of the field it replaces — a label bar and a field bar — so the layout does not shift when the real thing lands.

Do not use a skeleton for a field waiting on a check. That is an async state and belongs inside the field, not in place of it.

Validation

Timing

Validate on blur, not on every keystroke. Marking a half-typed answer as invalid is telling someone off for not having finished. The exception is a live constraint someone is working against — a character counter, which is feedback rather than judgement.

Once a field has shown an error, switch it to validating on input, so the message clears the moment it is fixed rather than waiting for another blur.

Form-level errors

For a whole-form failure, put a summary at the top listing each bad field as a link, and move focus to it on submit. Someone at the bottom of a long form should not have to hunt upward for what went wrong.

Motion

Border and shadow transition over --transition-interactive, 140ms. The error state appears without a transition — a validation message that fades in reads as uncertain.

Accessibility

Most of a field's accessibility comes from three relationships: label to control, description to control, and error to control. Items marked high risk are the ones that come up most often in review.

Text input and textarea

The base of every form. Label binding is not optional.

  • 3.3.2A persistent visible label — placeholder-only fields fail. Format hints are stated before entry, not after the first error. high risk
  • 1.3.1Label bound with for and id; hints and errors linked through aria-describedby. high risk
  • 1.4.11The field border reaches 3:1. Pale grey 1px borders are the single most common failure in any design system. high risk
  • 2.4.7The focus style is distinguishable from the error style — a field can be both at once.
  • 4.1.2Required and invalid exposed through aria-required and aria-invalid, not by an asterisk or a colour.
  • 1.4.12No fixed height; the field grows with the reader's own text spacing.
  • 1.4.3Value, label, hint and error all reach 4.5:1 — including the placeholder, which most systems leave too pale to read.
  • 2.5.3If a field carries both a visible label and an aria-label, the visible text is contained in the accessible name.

Errors and help

An error nobody hears is an error nobody fixes.

  • 3.3.1The error is identified in text, not by a red border alone. high risk
  • 3.3.3The message suggests a correction where one can be worked out.
  • 4.1.3A form-level error summary announced through a live region, with focus moved to it.
  • 2.4.6Labels and hints describe the purpose; hints stay to one sentence.
  • 3.2.2No context change on input — the form does not submit, navigate or reorder itself when a field is filled or blurred.

Zoom and reflow

Where a form that passed review breaks on someone else's machine.

  • 1.4.10No horizontal scrolling at 320px. Side-by-side field pairs collapse to a single column. high risk
  • 1.4.4Text resizes to 200% without the field clipping its value or the label wrapping into it.
  • 2.4.11A focused field is not obscured by a sticky header or footer. Reserve scroll-padding on the root.

Label association

The label's for must match the input's id. That single link does three jobs: a screen reader announces the label with the field, clicking the label focuses the field, and the tap target grows to include the label text.

What you still have to do

  • Give every field a unique id and match it in the label.
  • Toggle aria-invalid as validation state changes.
  • Pair every asterisk with aria-required, and explain the asterisk once at the top of the form.
  • Provide an error summary on form-level failure and move focus to it.
  • Never rely on the red border alone — always pair it with an icon and a message.
