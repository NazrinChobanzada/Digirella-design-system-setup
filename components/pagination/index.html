Pagination New

Pagination splits a large result set into fixed pages, giving users a landmark in the data and a reliable way to jump to any position in it.

Overview

Pagination tells the user where they are in a data set and lets them move through it page by page or jump directly to any page. The minimum kit is a previous button, a sequence of page numbers, and a next button — plus a count that says "Page 3 of 21" so the user always knows the size of the job.

Guidelines

When to use

Pagination is not the only way to move through a long data set. The right choice depends on whether the total is known, whether items need to be findable by position, and whether the user needs a stable landing point.

PatternUse whenNot for
PaginationThe total is known, pages are bookmarkable, the user may want to jump to page 14 directly, or a footer must be reachable.Feeds and timelines where items have no stable position. Any context where the total is unknown or grows continuously.
Infinite scrollBrowsing feeds where the next item is always relevant and positional access is not needed — social timelines, image galleries.Results the user needs to compare, export, or audit. Any context with a footer or a sticky toolbar that must stay accessible.
Load moreA hybrid: the user decides when to extend the list. Better than infinite scroll when some items need to stay visible while more are added below.Very large sets where the user would have to click many times to reach a known item. Search results tables.
Rule of thumbIf the data set will produce more than two pages and items need to be findable, shareable or auditable by position, use pagination. Below two pages of results, no control is needed — just show all the items.

Page size

The number of rows per page determines how often the user must turn a page and how much data they can compare at once. Too few rows and every scan involves a page turn; too many and the table becomes a scroll.

SizeDefault?Use for
10—Mobile-first contexts and tables with dense rows (thumbnails, multi-line cells) where more than ten rows per screen would overwhelm.
25Recommended defaultMost product and data tables. Fits a 1280px screen at comfortable density without scrolling past the footer.
50—Power users comparing or auditing large sets, and compact-density tables where 50 rows fit without excessive scrolling.
100—Export-like workflows where the user wants the maximum before downloading. Rarely needed in browsing contexts.
DefaultStart at 25. It is enough data to give a meaningful sample and small enough to load quickly. Offer larger sizes only where the user's task genuinely involves scanning or comparing many rows at once.
User preferenceIf the product persists user settings, remember the last page size the user chose. A power user who always wants 50 rows should not have to reset that on every visit. Store it in user preferences, not just localStorage, so it follows them across devices.
Changing page sizeWhen the user changes the page size, reset to page 1. The current page offset is no longer meaningful — staying on "page 3" while switching from 25 to 50 rows per page shows the wrong slice of data.
pageSize: 10 | 25 | 50 | 100 · defaultPageSize: number · onPageSizeChange

Variants

Three variants, chosen by whether the total page count is known and how much space is available.

Numbered pages — default
Page 4 of 21

The full control set: previous, numbered pages with ellipsis, next, and a count. Use when the total is known and the data set has more than three pages. This is the default variant for all data tables.

Previous / next only — unknown total

When the backend uses cursor-based pagination and does not return a total, the page count is unknown. Show only previous and next. Never display page numbers you do not have — never guess or approximate the total.

Behaviour

Ellipsis

The ellipsis (…) collapses the middle of a long page sequence so the control stays compact. Three fixed rules govern which pages are shown at any point.

RuleWhy
Always show the first and last page.The user needs to know the boundaries of the data set and to jump to either end without clicking through pages.
Show N sibling pages on each side of the current page (default N=1).The user scans around the current position most often. One sibling on each side is enough for most tables; raise to 2 for very large sets where skipping one page at a time is too slow.
Collapse the rest with a single … on the side where pages are hidden.Two ellipses appear when the current page is in the middle of a long run. One ellipsis appears when the current page is close to either end.

Edge cases

SituationBehaviour
1 page totalHide the entire pagination component. A control for a data set of one page adds noise without any value.
2–3 pages totalShow all page numbers. No ellipsis is needed; the component shrinks naturally to fit the count.
On page 1The previous button is disabled (aria-disabled="true"). It must remain in the DOM and in the tab order — removing it causes focus to jump unexpectedly.
On the last pageThe next button is disabled (aria-disabled="true"). Same rule as above.
Page out of rangeIf a saved URL references page 50 of a set that now has 12 pages, clamp to the last page and update the URL. Never show an empty table with no explanation.
Data changes during sessionIf a filter reduces the total below the current page, reset to page 1. Staying on "page 4 of 2" is disorienting and shows an empty table without context.

Accessibility

Structure

The pagination component is a navigation landmark. Its markup must let screen reader users find it by landmark navigation and understand the current position within the data set.

  • 4.1.2Wrap the component in <nav aria-label="Pagination">. Two pagination controls on one screen (top and bottom) each need a distinct label — "Pagination, top" and "Pagination, bottom". high risk
  • 1.3.1Mark the current page with aria-current="page" on its button. The primary-colour fill is invisible to screen readers — the attribute is not optional. high risk
  • 2.4.6The landmark label "Pagination" makes the region findable by heading and landmark navigation without additional effort from the user.

Buttons and controls

  • 2.5.3The previous and next buttons must have descriptive accessible names: aria-label="Previous page" and aria-label="Next page". An accessible name of "‹" or "›" is not a name. high risk
  • 1.4.11The current-page button uses the primary fill. The on-primary label achieves 6.9:1 against that fill, which passes AA.
  • 2.1.1All buttons are reachable by Tab and activated by Enter or Space. The ellipsis is not a button and is omitted from the tab order.
  • 2.5.8Each page button is at least 34×34px, clearing the 24×24px WCAG 2.5.8 minimum target size.
  • 4.1.2Disabled previous/next buttons use aria-disabled="true", not the HTML disabled attribute, so they remain in the tab order and screen readers announce them as unavailable rather than simply absent.
