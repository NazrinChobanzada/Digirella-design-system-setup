<div class="page__eyebrow">Components</div><h1 class="page__title">Button <span class="flag flag--lg">New</span></h1><p class="page__lede">Buttons start an action. The label says what will happen when someone presses it.</p>
<div class="doc">


<section id="overview">
<h2>Overview</h2>
<p>Buttons let people act on the page. Because they carry the most visual weight of any control, their hierarchy is what tells someone where to go next — which is why the system allows one primary button per screen and pushes everything else down a level.</p>
<div class="demo">
<button type="button" class="btn btn--primary">Buy now</button>
<button type="button" class="btn btn--secondary">Add to cart</button>
</div>
<p class="caption">Every example on this page is the real component. Hover it, press it, tab to it.</p>
</section>

<div class="part" id="part-guidelines"><h2 class="part__title">Guidelines</h2></div><section id="principles" data-part="Guidelines">
<h2>Principles</h2>
<p>Four ideas explain most of the decisions on this page.</p>
<h3>One action should look like the answer</h3>
<p>A screen with two equally weighted buttons asks a question instead of offering a path. One primary per screen is not a style rule — it is what makes the page readable at a glance, and it holds inside dialogs and drawers too.</p>
<h3>Weight follows frequency, not value</h3>
<p>The most common action gets the most weight, even when a rarer one is worth more to the business. A checkout that shouts about its upsell and whispers "Continue" costs more than it earns.</p>
<h3>The label is the interface</h3>
<p>People read buttons before they read anything around them. A label that names its object — "Delete listing" — completes the sentence on its own; one that says "OK" sends the reader back to the paragraph above to find out what they are agreeing to.</p>
<h3>Never dead-end someone</h3>
<p>A button that cannot be pressed and does not say why is a wall. Either explain what would enable it, or leave it enabled and explain the problem after the press — the second is usually better, because it lets people find out by trying.</p><p>Two or three related actions can sit together. Beyond three, move the extras into a menu — a row of five buttons makes the important one harder to find, not easier.</p>
<div class="dodont">
<div class="dodont__item" data-kind="do"><div class="dodont__stage">
<button type="button" class="btn btn--primary">Publish</button>
<button type="button" class="btn btn--ghost">Save draft</button>
<button type="button" class="btn btn--ghost">Preview</button>
</div><div class="dodont__note"><b>Do</b> keep one action prominent and let the rest recede.</div></div>
<div class="dodont__item" data-kind="dont"><div class="dodont__stage">
<button type="button" class="btn btn--secondary">Publish</button>
<button type="button" class="btn btn--secondary">Save</button>
<button type="button" class="btn btn--secondary">Preview</button>
<button type="button" class="btn btn--secondary">Share</button>
</div><div class="dodont__note"><b>Don't</b> line up four equal-weight buttons with no hierarchy.</div></div>
</div>
</section>

<section id="when-not-to-use-a-button">
<h2>When not to use a button</h2>
<p>Use a button when pressing it <strong>does</strong> something: submits a form, opens a dialog, adds to a cart, deletes a listing. One primary button per screen, and everything else at a lower emphasis.</p><p>Don't use a button to move someone to another page — that's a link. If the action changes the address bar and can be opened in a new tab, it's navigation, and it should be marked up as <code>&lt;a&gt;</code>. Styling a link like a button is fine when it's a call to action; using a <code>&lt;button&gt;</code> for navigation is not, because it breaks middle-click, right-click, and screen reader expectations.</p>

<div class="dodont">
<div class="dodont__item" data-kind="do"><div class="dodont__stage">
<button type="button" class="btn btn--primary">Place order</button>
<button type="button" class="btn btn--ghost">Cancel</button>
</div><div class="dodont__note"><b>Do</b> pair one primary action with a lower-emphasis escape.</div></div>
<div class="dodont__item" data-kind="dont"><div class="dodont__stage">
<button type="button" class="btn btn--primary">Place order</button>
<button type="button" class="btn btn--primary">Save for later</button>
</div><div class="dodont__note"><b>Don't</b> put two primary buttons side by side — neither one wins.</div></div>
</div>
</section>

<h2>Anatomy</h2>
<div class="demo anatomy">

<p>Unlike some systems, Digirella centres the label rather than left-aligning it. Buttons here are sized to their content instead of running full width, so centring reads as intentional rather than lopsided.</p>

<h3>Icons</h3>
<p>Any variant can carry an icon. It sits to the left of the label at 16px, separated by <code>--space-3</code>, and inherits <code>currentColor</code> — so no variant needs its own icon rule, and the icon changes colour with the button through every state.</p>

<section id="variants">
<h2>Variants</h2>
<p>Each variant has a job. The decision is always the same two questions: does this action need brand weight, and does its container need to be visible?</p>
<table>
<thead><tr><th style="width:88px">Variant</th><th style="width:150px">Example</th><th>Use for</th><th>Don't use for</th></tr></thead>
<tbody><tr><td>Primary</td><td><button type="button" class="btn btn--primary">Buy now</button></td><td class="use">The single most important action — submit, confirm, continue, buy. Once per screen, and once more inside any dialog or drawer.</td><td class="use">A second primary anywhere on the same screen. Destructive actions. Low-stakes actions like “Preview”.</td></tr><tr><td>Secondary</td><td><button type="button" class="btn btn--secondary">Add to cart</button></td><td class="use">A second action that still deserves brand weight — the step taken <em>before</em> the primary one, like “Search” beside “Save”.</td><td class="use">“Cancel” or “Back”, which are exits rather than choices. More than twice on a screen. Tinted backgrounds, where the border loses its 3:1.</td></tr><tr><td>Tertiary</td><td><button type="button" class="btn btn--tertiary">Back</button></td><td class="use">Supporting actions that need a visible container but no brand weight — “Back”, “Export”, toolbar actions of equal low importance.</td><td class="use">The only button on a screen. Long lists, where stacked borders become noise.</td></tr><tr><td>Ghost</td><td><button type="button" class="btn btn--ghost">Cancel</button></td><td class="use">Dismissals and cancels, and repeated actions in dense rows where a container would add weight to the thing you least want pressed.</td><td class="use">The primary action — it will be missed. Busy backgrounds where the label drops below 4.5:1.</td></tr><tr><td>Danger</td><td><button type="button" class="btn btn--danger">Delete listing</button></td><td class="use">Irreversible or costly actions, always as the confirming button inside a confirmation dialog.</td><td class="use">The trigger that <em>opens</em> the confirmation — that one is a normal button. Actions that are merely unusual. More than once per screen.</td></tr></tbody>
</table>

<p>A button with no label at all is a different component with its own sizing, hit area and naming rules: see <a href="../../components/icon-button/">IconButton</a>. It is not a sixth variant here, because nothing on this page applies to it unchanged.</p>

<h3>Type</h3>
<p>Labels are <code>--font-sans</code> at weight 600 with a line height of 1. Semibold rather than bold: at button sizes, 700 starts to look heavier than the surrounding interface.</p>

<h3>Focus ring</h3>
<p>Two rings. Every variant uses <code>--focus-ring</code> — 2px of <code>--color-primary</code> at 2px offset — except danger, which rings in <code>--border-danger</code>. A destructive control that turns brand-green at the moment of keyboard focus is throwing away its warning exactly when someone is about to press Enter.</p>

<section id="sizes">

<h3>A variant is not a state</h3>
<p>A primary button does not become a danger button, and a secondary does not become a primary. If a screen needs both readings it needs <strong>two buttons</strong>, ordered by priority or by the step they belong to — and one layout still holds one primary.</p>
<p>People locate a button by its weight and colour before they read it. A control that changes variant between states relocates itself while you are looking at it.</p>
<p>Some inventories treat <code>danger</code> and <code>ghost</code> as states of a button rather than variants of it. Here they are variants, for exactly that reason. The only state among them is disabled.</p>

<p>Two rules hold in any language: <strong>name the action</strong>, and <strong>keep it short</strong>. "Sepete əlavə et" and "Add to cart" are the same instruction; "OK" and "Bəli" are the same failure, because both make someone re-read the surrounding text to work out what they are agreeing to.</p>
<p>Three words is the working limit in English. Agglutinative languages run longer for the same meaning, so judge by rendered width rather than word count — if the label wraps to a second line, it is doing the job of the surrounding copy.</p>

<section id="disabled">
<h2>Disabled</h2>
<p>Disabled is a <strong>state</strong>, not a variant — but it has to read as <em>off</em> before it reads as which variant it was. Three signals do that, and none of them is hue, so the state survives a monochrome print and a colour-blind reader.</p>
<ol class="dos">
<li>The label drops from 600 to 400. A lighter label is the one cue that needs no colour at all.</li>
<li>Every container loses its brand colour, and a border may only get <em>weaker</em> than its enabled state — never stronger, and never a different hue. An earlier version turned the disabled secondary border green, which read as &ldquo;selected&rdquo;; another gave disabled tertiary a border it did not have when enabled, so disabling a control made it gain structure.</li>
<li><code>cursor: not-allowed</code>, and no hover or active response whatsoever.</li>
</ol>
<p>Identity is what is left over, and it is carried by <em>construction</em> rather than by hue — five variants, five shapes:</p>

<p>Labels stay at or above 4.17:1. WCAG exempts inactive controls from the contrast thresholds, so most systems let disabled buttons fall to around 2:1 — legible only if you already know what they say. Ours stays readable on purpose: someone has to be able to read the thing they cannot press in order to work out why. The faded borders <em>do</em> sit below 3:1, and that is deliberate — the container should read as off.</p>
<h3>disabled or aria-disabled</h3>
<p>The <code>disabled</code> attribute removes the button from the tab order entirely, which is right when the control is irrelevant. When the control is relevant but not yet available — a submit button waiting on a required field — prefer <code>aria-disabled="true"</code>: it keeps the button focusable and announced, so someone navigating by keyboard can find it and read why it is blocked. Both render identically here.</p>
<div class="callout"><div><b>A disabled button with no reason next to it is a dead end.</b> If someone can't press it, say what would make it pressable &mdash; &ldquo;Add at least one photo to publish&rdquo; &mdash; in helper text nearby. Otherwise leave it enabled and explain the problem after the press, which is usually the better pattern.</div></div>

<h3>Giving the reason, so it reaches the keyboard too</h3>
<p>The <code>disabled</code> attribute removes the button from the tab order, which also removes any tooltip attached to it: <code>:focus-within</code> never fires on something that cannot take focus, so a keyboard user gets the dead end and no explanation. <code>aria-disabled="true"</code> keeps the control focusable and announced, so the reason is reachable both ways.</p>
<div class="demo">
<span class="tip">
<button type="button" class="btn btn--primary" aria-disabled="true" aria-describedby="why-publish">Publish listing</button>
<span class="tip__bubble" id="why-publish" role="tooltip" data-placement="top">Add at least one photo to publish</span>
</span>
<button type="button" class="btn btn--primary" disabled>Publish listing</button>
</div>
<p class="caption">Hover or tab to the first button &mdash; the reason appears, and a screen reader announces it through <code>aria-describedby</code>. The second uses <code>disabled</code>: tab past it and nothing is reachable, because there is nothing to focus.</p>
<div class="callout"><div><b><code>aria-disabled</code> does not stop the click.</b> It changes what the control is <em>announced</em> as, nothing more — the element is still focusable, still in the tab order, and its handler still fires on Enter, Space and pointer. Blocking the action is your job: return early in the handler. A button that looks disabled, reads as disabled, and then runs anyway is worse than one that was never disabled at all.</div></div>
<div class="code"><pre><code>&lt;button aria-disabled="true" aria-describedby="why"&gt;Publish listing&lt;/button&gt;

button.addEventListener("click", (e) =&gt; {
if (button.getAttribute("aria-disabled") === "true") return; // ← required
publish();
});</code></pre></div>
<p>That is the trade: <code>disabled</code> blocks the action for free but takes the control out of reach; <code>aria-disabled</code> keeps it reachable but hands you the blocking. Use <code>disabled</code> when there is nothing to explain, and <code>aria-disabled</code> whenever there is.</p>

<div class="dodont__item" data-kind="dont"><div class="dodont__stage">
<button type="button" class="btn btn--secondary" disabled title="Your cart is empty">Go to checkout</button>
</div><div class="dodont__note"><b>Don't</b> hang the reason off <code>title</code> on a <code>disabled</code> button &mdash; it is unreachable by keyboard and unreliable on touch.</div></div>
</div>

<section id="loading">

<h3>Keep the button; change its state</h3>
<p>A control that appears in the layout as a result of something else is not expected. If an action is not available yet, it is shown disabled rather than hidden — the layout keeps its shape and the action stays discoverable.</p>
<p>That sits next to the advice above, which prefers leaving a button enabled and explaining the problem after the press. Both avoid the same failure from different directions, so the order matters:</p>
<ol class="dos">
<li><strong>Keep it enabled</strong> and explain the problem on press. Someone finds out by trying, which is the shortest path to understanding.</li>
<li>If it genuinely must be unavailable, <strong>show it disabled with a reason</strong>. Never hide it.</li>
<li><strong>Never hide and reveal.</strong> The layout jumps, and an action nobody has seen cannot be planned for.</li>
</ol>
<h2>Loading</h2>
<p>A loading button is <strong>busy</strong>, not unavailable — so it keeps its variant colour and its label, and adds a spinner. Greying it out would say "you can't do this", when the truth is "it's already happening", and it discards the hierarchy at the exact moment someone is watching for a result.</p>
<div class="demo">
<button type="button" class="btn btn--primary" data-loading="true" aria-busy="true"><span class="spinner" aria-hidden="true"></span>Placing order</button>
<button type="button" class="btn btn--secondary" data-loading="true" aria-busy="true"><span class="spinner" aria-hidden="true"></span>Saving</button>

<section id="motion">
<h2>Motion</h2>
<p>Buttons use <code>--transition-interactive</code>, which is 140ms on <code>--ease-standard</code>, applied to background, border and colour. Nothing else animates — no scaling on press, no shadow bloom on hover.</p>
<p>Under <code>prefers-reduced-motion</code>, transitions drop to 1ms rather than being removed, so the state change still registers as a change.</p>
</section>

<h2>Accessibility</h2>
<p>The criteria below are the ones a button can actually fail. Items marked <span class="risk">high risk</span> are the ones that come up most often in review.</p>

<div class="wcag">
<div class="wcag__group"><h3>Every button</h3>
<p>Most of this comes free from a native <code>&lt;button&gt;</code> and has to be rebuilt by hand on anything else.</p>
<ul class="wcag__list"><li><span class="sc">2.1.1</span><span>Operable with Enter and Space, and reachable by Tab.</span></li><li><span class="sc" data-risk="high">2.5.3</span><span>The accessible name contains the visible label word for word. An <code>aria-label</code> that paraphrases breaks voice control. <span class="risk">high risk</span></span></li><li><span class="sc" data-risk="high">1.4.11</span><span>The container reaches 3:1 against the page. Secondary sits at 6.85:1, tertiary at 3.12:1. <span class="risk">high risk</span></span></li><li><span class="sc">2.4.7</span><span>A visible focus indicator, 2px at 2px offset, on every variant.</span></li><li><span class="sc">2.5.8</span><span>At least 24 × 24px. <p>The classic silent failure: visually obvious, invisible to a screen reader.</p>

<p>A visible label is the accessible name, so most buttons need nothing extra. Two cases do: icon-only buttons need <code>aria-label</code>, and repeated labels need disambiguating — five "Edit" buttons in a table should each name their row, as <code>aria-label="Edit iPhone 14 Pro"</code>.</p>

<div class="part" id="part-specification"><h2 class="part__title">Specification</h2></div><section id="spacing" data-part="Specification">

<h3>Naming a button that has no text</h3>
<p>A button whose label is an icon still needs a name. This system puts it in <code>aria-label</code> on <a href="../../components/icon-button/">IconButton</a> and marks the glyph <code>aria-hidden="true"</code>. Visually hidden text inside the button reaches the same result and is the better choice when the name has to be selectable or translated in the page; an <code>&lt;img&gt;</code> used as the label carries it in <code>alt</code> instead. Pick one — a button with all three is announced three times.</p>
<h2>Spacing</h2>
<p>Horizontal padding by size; no vertical padding at all — the height token plus flex centring sets the box.</p>
<table><thead><tr><th style="width:250px">Context</th><th style="width:150px">Value</th><th>Token</th></tr></thead><tbody><tr><td>Height</td><td class="val">30 / 38 / 46</td><td class="tok">--control-height-sm/md/lg</td></tr><tr><td>Padding</td><td class="val">0 × 12 / 16 / 20</td><td class="tok">--button-padding-x-sm/md/lg</td></tr><tr><td>Icon to label</td><td class="val">8</td><td class="tok">--button-icon-gap</td></tr><tr><td>Button to button</td><td class="val">8</td><td class="tok">--button-group-gap</td></tr><tr><td>Minimum width</td><td class="val">80</td><td class="tok">--button-min-width</td></tr></tbody></table>
<p>Two or three buttons in a row sit 8px apart; 12px in a comfortable-density layout. Buttons that belong to <em>different</em> tasks take <code>--space-5</code> instead, so the row does not read as one group of choices.</p>
<table><thead><tr><th style="width:130px">Size</th><th style="width:110px">Height</th><th style="width:160px">Padding V / H</th><th>Type</th></tr></thead><tbody>
<tr><td>Small</td><td class="val">30px</td><td class="val">0 / 12px</td><td class="tok">--type-control-sm-size</td></tr>
<tr><td>Medium</td><td class="val">38px</td><td class="val">0 / 16px</td><td class="tok">--type-control-size</td></tr>
<tr><td>Large</td><td class="val">46px</td><td class="val">0 / 20px</td><td class="tok">--type-control-lg-size</td></tr>
</tbody></table><p>A button beside a field needs no adjustment: the default button and every form field are both 38px, so they align on one line. That is why the default is 38 rather than the 40 most systems use.</p><p>The minimum width is what stops a short label like “OK” from looking cramped. It does not apply to icon-only buttons, which are their own component.</p><p class="caption">Values are read from <code>tokens/spacing-components.css</code>. The rules behind them, and the two places this system diverges from the consensus, are on the <a href="../../foundations/spacing/">spacing</a> page.</p>
</section>

<section id="elevation" data-part="Specification">
<h2>Elevation</h2>
<p>Flat at every size and in every state. A button darkens on hover; it never lifts.</p>
<table><thead><tr><th style="width:230px">Surface</th><th style="width:210px">Level</th><th>Token</th></tr></thead><tbody><tr><td>Rest, hover, press</td><td class="val">level 0</td><td class="tok">--elevation-flat</td></tr><tr><td>Focus</td><td class="val">ring, not a shadow</td><td class="tok">--focus-ring</td></tr><tr><td>Disabled</td><td class="val">level 0</td><td class="tok">--elevation-flat</td></tr></tbody></table>
<p>A button is small enough that a background change is the clearer signal. Lifting is reserved for large targets like a card, where a shadow alone would read as a colour change.</p><p>The only exception anywhere is a button inside a floating layer — the layer carries the shadow, never the button.</p><p class="caption">The four levels and the rules behind them are on the <a href="../../foundations/elevation/">elevation</a> page.</p>
</section>
