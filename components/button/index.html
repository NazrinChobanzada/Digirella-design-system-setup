Button New

Buttons start an action. The label says what will happen when someone presses it.

Overview

Buttons let people act on the page. Because they carry the most visual weight of any control, their hierarchy is what tells someone where to go next — which is why the system allows one primary button per screen and pushes everything else down a level.

Every example on this page is the real component. Hover it, press it, tab to it.

Guidelines

Principles

Four ideas explain most of the decisions on this page.

One action should look like the answer

A screen with two equally weighted buttons asks a question instead of offering a path. One primary per screen is not a style rule — it is what makes the page readable at a glance, and it holds inside dialogs and drawers too.

Weight follows frequency, not value

The most common action gets the most weight, even when a rarer one is worth more to the business. A checkout that shouts about its upsell and whispers "Continue" costs more than it earns.

The label is the interface

People read buttons before they read anything around them. A label that names its object — "Delete listing" — completes the sentence on its own; one that says "OK" sends the reader back to the paragraph above to find out what they are agreeing to.

Never dead-end someone

A button that cannot be pressed and does not say why is a wall. Either explain what would enable it, or leave it enabled and explain the problem after the press — the second is usually better, because it lets people find out by trying.

Two or three related actions can sit together. Beyond three, move the extras into a menu — a row of five buttons makes the important one harder to find, not easier.

Do keep one action prominent and let the rest recede.
Don't line up four equal-weight buttons with no hierarchy.

When not to use a button

Use a button when pressing it does something: submits a form, opens a dialog, adds to a cart, deletes a listing. One primary button per screen, and everything else at a lower emphasis.

Don't use a button to move someone to another page — that's a link. If the action changes the address bar and can be opened in a new tab, it's navigation, and it should be marked up as <a>. Styling a link like a button is fine when it's a call to action; using a <button> for navigation is not, because it breaks middle-click, right-click, and screen reader expectations.

Do pair one primary action with a lower-emphasis escape.
Don't put two primary buttons side by side — neither one wins.

Variants and style

Anatomy

  • 1 Container — sets the variant colour and the 4px control radius.
  • 2 Icon — optional, 16px, always to the left of the label.
  • 3 Label — names the action, centred.

Unlike some systems, Digirella centres the label rather than left-aligning it. Buttons here are sized to their content instead of running full width, so centring reads as intentional rather than lopsided.

Icons

Any variant can carry an icon. It sits to the left of the label at 16px, separated by --space-3, and inherits currentColor — so no variant needs its own icon rule, and the icon changes colour with the button through every state.

The icon scales with the size step — 14, 16 and 18px — so the optical weight against the label stays constant.

The icon is decorative: it takes aria-hidden="true" and the label carries the meaning. An icon that needs to be understood on its own belongs on an icon-only button, which has an aria-label instead.

One icon, on the left, reinforcing the label.
Icons on both sides give the eye two places to start.

Variants

Each variant has a job. The decision is always the same two questions: does this action need brand weight, and does its container need to be visible?

Type

Labels are --font-sans at weight 600 with a line height of 1. Semibold rather than bold: at button sizes, 700 starts to look heavier than the surrounding interface.

Focus ring

Two rings. Every variant uses --focus-ring — 2px of --color-primary at 2px offset — except danger, which rings in --border-danger. A destructive control that turns brand-green at the moment of keyboard focus is throwing away its warning exactly when someone is about to press Enter.

A variant is not a state

A primary button does not become a danger button, and a secondary does not become a primary. If a screen needs both readings it needs two buttons, ordered by priority or by the step they belong to — and one layout still holds one primary.

People locate a button by its weight and colour before they read it. A control that changes variant between states relocates itself while you are looking at it.

Some inventories treat danger and ghost as states of a button rather than variants of it. Here they are variants, for exactly that reason. The only state among them is disabled.

Don't mix sizes inside one group. If a row of buttons needs different weights, change the variant, not the height.

Labels

Two rules hold in any language: name the action, and keep it short. "Sepete əlavə et" and "Add to cart" are the same instruction; "OK" and "Bəli" are the same failure, because both make someone re-read the surrounding text to work out what they are agreeing to.

Three words is the working limit in English. Agglutinative languages run longer for the same meaning, so judge by rendered width rather than word count — if the label wraps to a second line, it is doing the job of the surrounding copy.

Name the object so the action stands on its own.
A bare confirmation says nothing about the consequence.
Casing and word order are language decisions, not system decisions. The English rules here — sentence case, verb before object — do not transfer. Turkish and Azerbaijani put the verb last, and capitalisation conventions differ. Set those rules once per locale in your content guidelines; the system only asks that labels are specific and short.

Long labels wrap rather than truncate. A clipped label is unreadable; a wrapped one is merely tall.

Behaviour

States

Five states, all reachable in the demo above. Hover darkens by one step; press darkens again with no scaling; focus draws a 2px ring at 2px offset; disabled drops to a neutral ground with a not-allowed cursor.

The middle three are painted swatches showing the target colours — the live buttons either side of them react for real.

Interaction

A press anywhere inside the container triggers the button. From the keyboard, Enter and Space both activate it, and the focus ring appears only for keyboard users because the system uses :focus-visible.

Disabled

Disabled is a state, not a variant — but it has to read as off before it reads as which variant it was. Three signals do that, and none of them is hue, so the state survives a monochrome print and a colour-blind reader.

  1. The label drops from 600 to 400. A lighter label is the one cue that needs no colour at all.
  2. Every container loses its brand colour, and a border may only get weaker than its enabled state — never stronger, and never a different hue. An earlier version turned the disabled secondary border green, which read as “selected”; another gave disabled tertiary a border it did not have when enabled, so disabling a control made it gain structure.
  3. cursor: not-allowed, and no hover or active response whatsoever.

Identity is what is left over, and it is carried by construction rather than by hue — five variants, five shapes:

Enabled
Disabled

Compare with the enabled row in Variants — the shapes line up, the colour drains.

Labels stay at or above 4.17:1. WCAG exempts inactive controls from the contrast thresholds, so most systems let disabled buttons fall to around 2:1 — legible only if you already know what they say. Ours stays readable on purpose: someone has to be able to read the thing they cannot press in order to work out why. The faded borders do sit below 3:1, and that is deliberate — the container should read as off.

disabled or aria-disabled

The disabled attribute removes the button from the tab order entirely, which is right when the control is irrelevant. When the control is relevant but not yet available — a submit button waiting on a required field — prefer aria-disabled="true": it keeps the button focusable and announced, so someone navigating by keyboard can find it and read why it is blocked. Both render identically here.

A disabled button with no reason next to it is a dead end. If someone can't press it, say what would make it pressable — “Add at least one photo to publish” — in helper text nearby. Otherwise leave it enabled and explain the problem after the press, which is usually the better pattern.

Giving the reason, so it reaches the keyboard too

The disabled attribute removes the button from the tab order, which also removes any tooltip attached to it: :focus-within never fires on something that cannot take focus, so a keyboard user gets the dead end and no explanation. aria-disabled="true" keeps the control focusable and announced, so the reason is reachable both ways.

Add at least one photo to publish

Hover or tab to the first button — the reason appears, and a screen reader announces it through aria-describedby. The second uses disabled: tab past it and nothing is reachable, because there is nothing to focus.

aria-disabled does not stop the click. It changes what the control is announced as, nothing more — the element is still focusable, still in the tab order, and its handler still fires on Enter, Space and pointer. Blocking the action is your job: return early in the handler. A button that looks disabled, reads as disabled, and then runs anyway is worse than one that was never disabled at all.
<button aria-disabled="true" aria-describedby="why">Publish listing</button>

button.addEventListener("click", (e) => {
  if (button.getAttribute("aria-disabled") === "true") return;  // ← required
  publish();
});

That is the trade: disabled blocks the action for free but takes the control out of reach; aria-disabled keeps it reachable but hands you the blocking. Use disabled when there is nothing to explain, and aria-disabled whenever there is.

Your cart is empty
Do pair aria-disabled with a reason a keyboard can reach.
Don't hang the reason off title on a disabled button — it is unreachable by keyboard and unreliable on touch.

Keep the button; change its state

A control that appears in the layout as a result of something else is not expected. If an action is not available yet, it is shown disabled rather than hidden — the layout keeps its shape and the action stays discoverable.

That sits next to the advice above, which prefers leaving a button enabled and explaining the problem after the press. Both avoid the same failure from different directions, so the order matters:

  1. Keep it enabled and explain the problem on press. Someone finds out by trying, which is the shortest path to understanding.
  2. If it genuinely must be unavailable, show it disabled with a reason. Never hide it.
  3. Never hide and reveal. The layout jumps, and an action nobody has seen cannot be planned for.

Loading

A loading button is busy, not unavailable — so it keeps its variant colour and its label, and adds a spinner. Greying it out would say "you can't do this", when the truth is "it's already happening", and it discards the hierarchy at the exact moment someone is watching for a result.

Each button keeps its own colour while busy. Add a <span class="spinner"> before the label and set data-loading="true" with aria-busy="true". The spinner inherits currentColor, so it needs no per-variant rule.

LoadingDisabled

Trigger it past about 400ms — below that the spinner flashes and reads as a glitch. Keep the width fixed while loading so the row does not reflow, and change the label to the running form of the action: "Place order" becomes "Placing order". When it finishes, announce the result somewhere with role="status"; the button reports that it was pressed, not what happened next.

Motion

Buttons use --transition-interactive, which is 140ms on --ease-standard, applied to background, border and colour. Nothing else animates — no scaling on press, no shadow bloom on hover.

Under prefers-reduced-motion, transitions drop to 1ms rather than being removed, so the state change still registers as a change.

Accessibility

The criteria below are the ones a button can actually fail. Items marked high risk are the ones that come up most often in review.

Every button

Most of this comes free from a native <button> and has to be rebuilt by hand on anything else.

  • 2.1.1Operable with Enter and Space, and reachable by Tab.
  • 2.5.3The accessible name contains the visible label word for word. An aria-label that paraphrases breaks voice control. high risk
  • 1.4.11The container reaches 3:1 against the page. Secondary sits at 6.85:1, tertiary at 3.12:1. high risk
  • 2.4.7A visible focus indicator, 2px at 2px offset, on every variant.
  • 2.5.8At least 24 × 24px. Ours are 30, 38 and 46px tall.
  • 2.5.2Activation fires on pointer-up, so dragging off before release cancels it.
  • 1.4.1Loading and destructive states are not signalled by colour alone. This also drives the ghost rule below. high risk
  • 1.4.3Labels reach 4.5:1 in every variant, including on hover and active fills.
  • 4.1.2Name, role and value are programmatically determined, and changes are announced.

Icon-only

The classic silent failure: visually obvious, invisible to a screen reader.

  • 1.1.1A required aria-label. The icon supplies no name of its own. high risk
  • 2.5.8Hit area padded to 24px even when the glyph is 16px. high risk
  • 2.5.3If a tooltip shows a label, that same text is the accessible name.
  • 4.1.2Toggle icon buttons expose aria-pressed, not just a colour change.

Zoom, reflow and text spacing

The criteria a button passes at design time and fails the moment someone changes their own settings.

  • 1.4.4Text resizes to 200% without the label being clipped or the button losing its action.
  • 1.4.10No horizontal scrolling at 320px. Button groups wrap rather than overflow.
  • 1.4.12No fixed height. The button grows when the reader increases line height, letter spacing or word spacing. high risk
  • 1.4.11Focus rings survive at 200% zoom without being clipped by an ancestor with overflow: hidden.

Links styled as buttons

An anchor that looks like a button is still an anchor, and inherits an anchor's rules.

  • 2.1.1No role="button" on an anchor — it promises Space activation that anchors do not deliver. high risk
  • 2.4.4The link text describes the destination on its own.
  • 4.1.2A link opening a new tab announces it in its accessible name.
  • 1.4.3A link cannot take the disabled attribute, so it never gets the inactive-control exemption. A "disabled" link must still reach 4.5:1 — remove it or make it plain text instead. high risk

Ghost buttons need a second cue

A ghost button has no container at rest, so the only thing marking it as interactive is the colour of its text. WCAG 1.4.1 says colour cannot be the sole means of conveying that something is actionable — which makes a bare ghost button a real, if widely ignored, failure.

Give every ghost button a leading icon, or place it in a group where its neighbours establish the row as a set of controls. Both give the eye something other than hue to work with.

An icon marks it as a control without adding a container.
Alone on a page, this is indistinguishable from a heading.

The exception is a ghost button sitting beside other buttons — "Cancel" next to "Save" reads as a control because of the company it keeps.

Naming

A visible label is the accessible name, so most buttons need nothing extra. Two cases do: icon-only buttons need aria-label, and repeated labels need disambiguating — five "Edit" buttons in a table should each name their row, as aria-label="Edit iPhone 14 Pro".

What you still have to do

  • Give icon-only buttons a name.
  • Disambiguate repeated labels in lists and tables.
  • Announce the result of an action with role="status", or move focus to what changed. The button reports that it was pressed, not what happened next.
  • Explain any disabled state in adjacent text.

Specification

Naming a button that has no text

A button whose label is an icon still needs a name. This system puts it in aria-label on IconButton and marks the glyph aria-hidden="true". Visually hidden text inside the button reaches the same result and is the better choice when the name has to be selectable or translated in the page; an <img> used as the label carries it in alt instead. Pick one — a button with all three is announced three times.

Elevation

Flat at every size and in every state. A button darkens on hover; it never lifts.

SurfaceLevelToken
Rest, hover, presslevel 0--elevation-flat
Focusring, not a shadow--focus-ring
Disabledlevel 0--elevation-flat

A button is small enough that a background change is the clearer signal. Lifting is reserved for large targets like a card, where a shadow alone would read as a colour change.

The only exception anywhere is a button inside a floating layer — the layer carries the shadow, never the button.
